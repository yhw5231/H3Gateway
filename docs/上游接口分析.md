# 上游接口分析

本文记录 MiniMax-H3 匿名试用通道的**实测行为**。所有结论都来自对线上服务的直接
探测（Go 客户端，绕开本机 Schannel 的 TLS 问题），而不是对前端代码的猜测。

分析对象：`https://siftq.com`，前端 bundle `https://siftq.com/assets/main-hDBKOd1R.js`
（约 3.5 MB）。

---

## 2. 配额键：`X-Forwarded-For` 的原始字符串

**结论：上游按请求头 `X-Forwarded-For` 的第一个值计配额，比较时是原始字符串，
不做任何 IP 规范化。**

### 证据

| 实验 | 结果 |
| --- | --- |
| 用值 `A` 提交 → 读 `/usage` | `remaining` 从 2 降到 1 |
| 再用值 `A` 提交 | 成功，`remaining` 降到 0 |
| 第三次用值 `A` 提交 | `429 rate_limit_error` |
| 用全新值 `B` 提交 | 成功，`remaining` 独立为 1 |
| `198.51.100.9, 8.8.8.8` | 记在 `198.51.100.9`（第一个值生效） |
| `8.8.8.8, 198.51.100.9` | 记在 `8.8.8.8` |
| 值前后带空格 | 空格被 trim |

### 不做规范化的证据

以下每一对都被判定为**不同的**配额桶（各自独立消耗 2 次额度）：

| 形式 A | 形式 B |
| --- | --- |
| `2001:4860:4860:0:0:0:0:8888`（展开） | `2001:4860:4860::8888`（压缩） |
| `2A00:1450:4001:081B:0000:0000:0000:200E`（大写） | `2a00:1450:4001:81b::200e`（小写） |
| `2001:db8::1` | `[2001:db8::1]`（带方括号） |
| `198.51.100.9` | `198.51.100.09`（前导零） |
| `198.51.100.9` | `::ffff:198.51.100.9`（IPv4-mapped） |

### 完全没有校验

以下地址**全部被接受**并各自形成独立配额桶：

- `198.51.100.9`（TEST-NET-2，RFC 5737 文档段）
- `fd00::1234`（RFC 4193 唯一本地地址）
- `2001:db8::1`（RFC 3849 文档段）
- 任意随机公网地址

这说明上游只是把该字符串当成一个不透明的 key。

### 对网关的意义

只要每次请求换一个随机地址，额度就近乎无限。地址空间：

- IPv4：可选公网段约 2^24 量级（去掉保留段后）
- IPv6：`2000::/3` 内随机，约 2^61 量级

这也是网关默认 `xff_pool=public` 的原因（与原 Python 版一致）；
`reserved` 选项改用 RFC 5737 / RFC 3849 文档段，第三方更安全但桶空间小得多。

## 3. IPv6 支持实测

**结论：IPv6 形式的 `X-Forwarded-For` 与 IPv4 完全等价，是独立的配额键。**

### 方法：对照键（control key）

只用「提交前读一次、提交后读一次」是不足以证明的：如果上游**忽略**了请求头、
退回按真实出口 IP 计数，那么前后两次读数仍然会变化，测试会得出假阳性。

因此必须加一个对照：

1. 读目标键 `K` 的 `/usage` → 基线 `remaining`
2. 用 `K` 提交一次真实生成
3. 读 `K` 的 `/usage` → 应当减少
4. **读一个同族、全新未使用的对照键 `K'` 的 `/usage` → 应当仍是满额**

只有「`K` 减少 **且** `K'` 未被动过」才能证明配额由请求头决定。

### 线上实测输出

```
GET https://siftq.com/api/minimax-trial/usage 可达
IPv4 键 198.51.100.153 初始 remaining=2
IPv6 键 2001:db8:d671:abe8:11d3:b296:25a7:dfb2 初始 remaining=2
IPV4 提交成功（键 198.51.100.153），重新读取配额…
IPV4 提交后 remaining 2 -> 1
IPV4 对照键 203.0.113.33 remaining=2/2（未被扣减，说明配额按 XFF 计）
IPV4 结论：✅ 上游以 X-Forwarded-For 作为独立配额键
IPV6 提交成功（键 2001:db8:d671:abe8:11d3:b296:25a7:dfb2），重新读取配额…
IPV6 提交后 remaining 2 -> 1
IPV6 对照键 2001:db8:252d:f441:bb8f:9202:7400:4efc remaining=2/2（未被扣减，说明配额按 XFF 计）
IPV6 结论：✅ 上游以 X-Forwarded-For 作为独立配额键
```

### 端到端验证

用网关伪造随机 IPv6 地址（`2476:27b2:b8fd:1db4:bffb:3847:c12a:e502`）提交，
上游正常受理，任务最终 `succeeded`，视频 1.0 MB 并成功缓存到本地。

### 假阳性防护的自动化测试

`internal/xffprobe/xffprobe_test.go` 里用可编程假上游复现了两种情况：

- `ignoreIPv6=false`：IPv4、IPv6 都正确识别为配额键 → 断言两者均为「支持」
- `ignoreIPv6=true`：上游把非 IPv4 的值一律退回真实出口 IP → 断言 IPv6 为「不支持」

第二种情况正是只有前后对比时会产生假阳性的场景，测试确保对照键方法能识破它。

## 4. 请求格式要求

### multipart 分片必须带正确的 `Content-Type`

上游会校验图片分片的 `Content-Type`。使用 Go 的 `CreateFormFile`（固定写
`application/octet-stream`）会得到：

```
HTTP 415
{"type":"error","error":{"http_code":"415","type":"bad_request_error",
 "message":"Only JPG, PNG, or WEBP images are supported"}}
```

正确做法是嗅探图片真实类型（JPEG `FF D8 FF`、PNG `89 50 4E 47`、WEBP `RIFF....WEBP`），
用 `textproto.MIMEHeader` 手动构造分片头。网关已实现（`upstream.SniffImageMIME`）。

另外用 `bytes.Buffer` 整体缓冲请求体、以 `Content-Length` 发送（而不是 chunked），
兼容性更好。

### 表单字段

上游前端实际发送的字段：

| 字段 | 说明 |
| --- | --- |
| `ratio` | 例如 `9:16` |
| `duration` | 秒数，字符串形式 |
| `client_id` | 形如 `mmtrial_<random>`，标识本次会话 |
| `image` | 图片分片 |
| `visitorId` | 形如 `mmguest_<random>`（部分调用路径） |
| `channelCode` | 例如 `direct` |
| `sourceHost` | 来源标识 |

**注意：上游前端在该通道不发送 `prompt`。** 网关仍会把 `prompt` 字段转发上去，
但上游是否使用它未经证实——请在文档与 UI 中按「可能被忽略」对待。

### 请求头

| 头 | 说明 |
| --- | --- |
| `X-Forwarded-For` | 配额键，见上文 |
| `X-MiniMax-Trial-Client` | 与 `client_id` 一致 |
| `User-Agent` / `Referer` | 伪装成浏览器，网关默认已设置 |

## 5. showcase 通道已被登录墙拦截

原 Python 版走的是 `/showcase/video-generation` 并附带 `prompt`。该通道**现在需要登录**：

```
GET /api/minimax-trial/showcase/generation-decision?...
→ {"authenticated":false,"remaining":2,"busy":true,"estimated_credits":null,
   "balance":null,"action":"login"}

POST /api/minimax-trial/showcase/video-generation
→ HTTP 401
  {"type":"error","error":{"http_code":"401","type":"login_required",
   "message":"Sign in to see available generation options."}}
```

此外 showcase 素材列表里所有条目的 `contentCategory` 均为 `NSFW`。

**因此网关默认 `endpoint_mode=plain`。** `showcase` 代码路径保留，但只应在明确知道
上游已恢复匿名可用时才切换。

## 6. 时长与画幅限制

| 请求值 | 实际上游时长 |
| --- | --- |
| 4、5、6、7 | 6 秒 |
| 8、9、10、11、12 | 10 秒 |
| 13、14、15、16、20 | 15 秒 |

画幅：试用通道**只输出 9:16 竖屏**，其它比例被拒绝。网关对不支持的取值直接返回
`400`，而不是静默改成 9:16。

## 7. 并发与错误语义

- 上游 `max_concurrent` 报告为 5
- `429` + `rate_limit_error`：该配额键当日额度用尽 → 应轮换身份
- `401` + `login_required`：该身份被单独拦截 → 可轮换身份重试；连续多次失败说明是
  策略变更，应直接失败
- `5xx` / 网络错误：可重试，指数退避
- `4xx`（如 `415`）：请求本身有问题，重试无意义，直接失败

网关的重试策略即按此分类实现（`upstream.Error.IsRateLimit / IsAuthGate / IsRetryable`）。

## 8. 复现方法

```bash
# 直连上游做一次连通性检查（不消耗额度）
./h3gateway probe -dry-run

# 完整实测 IPv4/IPv6 配额键（每个族消耗 1 次生成额度，使用文档地址段）
./h3gateway probe

# 以 JSON 输出原始结论
./h3gateway probe -json

# 指定上游
./h3gateway probe -upstream https://siftq.com
```

后台「XFF / IPv6 测试」页面提供同样的功能，并会把结论持久化，供 `auto` 模式使用。
