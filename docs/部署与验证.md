## 3. 容器网络验证（关键约束）

**要求：只使用容器默认 bridge 网络，禁止创建项目网络。**

实现方式：`docker-compose.yml` 中服务声明 `network_mode: bridge`，且**整个文件没有
任何 `networks:` 段落**。

验证（完整的 `down` → `up` 循环）：

```bash
docker compose down
docker network ls --format '{{.Name}}' | sort > /tmp/before
docker compose up -d
docker network ls --format '{{.Name}}' | sort > /tmp/after
diff /tmp/before /tmp/after          # 无差异
docker inspect h3gateway --format '{{.HostConfig.NetworkMode}}'
```

实测输出：

```
before: bridge, host, ipv6-net, localcline_default, none,
        novelgenerationgo_default, yibiao-web_default, ythh_bangong_default, ythh-1_default
after : bridge, host, ipv6-net, localcline_default, none,
        novelgenerationgo_default, yibiao-web_default, ythh_bangong_default, ythh-1_default
RESULT: identical - no project network created

容器网络模式: bridge
```

> 列表里那些 `*_default` 网络是本机其它无关项目的，**启动前后完全一致**，证明本项目
> 没有新建任何网络。

`docker compose config` 也能确认这一点：输出中只有 `network_mode: bridge`，没有
`networks` 段。

## 4. 镜像构建

```bash
docker build --build-arg VERSION=0.1.0 -t h3gateway:latest .
```

构建要点：

- 构建阶段只复制 `go.mod`、`main.go`、`internal/`、`web/`；由于没有第三方依赖，
  不需要 `go mod download`，**离线可构建**
- `CGO_ENABLED=0` 静态编译，`-trimpath -ldflags="-s -w"` 减小体积
- 版本号通过 `-X main.version=${VERSION}` 注入，`./h3gateway version` 与后台都能看到
- 运行阶段安装 `ca-certificates`（访问上游需要）与 `tzdata`（控制台时间正确）
- 创建 uid/gid 10001 的非 root 用户 `h3` 运行
- `VOLUME /data`：JSON 数据库、视频缓存、上传原图都在这里
- `HEALTHCHECK` 走 `http://127.0.0.1:8787/healthz`

### 7.4 IPv6 配额键实测（后台「XFF / IPv6 测试」）

```
GET https://siftq.com/api/minimax-trial/usage 可达
IPv4 键 198.51.100.153 初始 remaining=2
IPv6 键 2001:db8:d671:abe8:11d3:b296:25a7:dfb2 初始 remaining=2

IPV6 提交成功（键 2001:db8:d671:abe8:11d3:b296:25a7:dfb2），重新读取配额…
IPV6 提交后 remaining 2 -> 1
IPV6 对照键 2001:db8:252d:f441:bb8f:9202:7400:4efc remaining=2/2（未被扣减，说明配额按 XFF 计）

```


### 7.5 一个地址两次生成（容量修复验证）

上游每个地址每天允许 2 次。修复前，网关在成功后把 `UsesLeft` 按上游返回的
`remaining` 赋值、又额外做了一次递减，导致地址只用 1 次就被退休，**有效容量减半**。

修复后连续提交两次，日志与统计：

```

task submitted task=video_877b5c5e22265803 xff=8.252.70.111 family=ipv4

rotator: { identities_minted: 1, identities_reused: 1, identities_exhausted: 1, pool_ready: 0 }

两个任务均 succeeded，各自缓存约 1.05 MB 的 MP4
```

同一个伪造地址（`8.252.70.111`）成功产出两条视频，用满 2 次额度后才被退休。

## 8. 发现并修复的问题

验证过程中发现并修复了以下真实缺陷（均有回归测试）：

| # | 问题 | 影响 | 修复 |
| --- | --- | --- | --- |
| 1 | `Submit` 在 `Start` 之前调用会 panic（`p.ctx` 为 nil） | 未启动轮询器时提交直接崩溃 | 在 `New` 里创建基础 context，`Start` 再基于调用方 context 重建 |
| 2 | 成功后身份被双重递减 | 每个地址只能用 1 次，**有效容量减半** | 采用上游返回的 `remaining` 作为权威值，不再额外递减；缺失该字段时才本地递减 |
| 3 | 上游返回体里的顶层字段没有被记录 | 无法区分「字段缺失」与「字段为 0」 | `do()` 里额外解析一份字段表 |
| 4 | dry-run 实测会声称 IPv6 可用 | 未做任何提交却给出「支持」结论，可能误导开启 IPv6 | dry-run 明确不置位任何 accepted 标记，并新增 `dry_run` 标识 |
| 5 | 未知 `/admin/api/*` 返回 200（落到 `/admin/` 子树，返回 SPA 页面） | 前端拿到 HTML 而不是 404，排错困难 | 在后台页面处理函数里拦截 `/admin/api/` 前缀并返回 404 |
| 6 | 设置接口静默钳制越界值 | 运维填错并发数会被悄悄改成 64，看不出问题 | 新增 `ValidateInput()`，越界直接 `400`；持久化加载路径仍走归一化修复 |
| 7 | `/v1/trial/usage` 暴露内部运维计数 | 公开接口泄露身份铸造/任务统计 | 收敛为只返回容量与生效模式 |
| 8 | 后台「重置」只清空地址池，不清计数 | 仪表盘数字不归零，与按钮语义不符 | `Reset()` 一并清零计数 |
| 9 | `chat/completions` 只取最后一条消息 | 末条是 assistant 时无法取图 | 改为回溯最后一条 user 消息 |
| 10 | 视频对象只有 `video_url` | 部分 OpenAI 风格客户端读 `url` | 两个字段同时返回 |
| 11 | **`/admin/admin.js`、`/admin/admin.css` 返回的是 HTML 外壳** | 浏览器拒绝把 HTML 当脚本执行，**整个后台控制台无法使用** | 新增 `GET /admin/{asset}` 单段路由按扩展名设置 `Content-Type`；`/admin/` 子树只服务控制台本身，其余路径返回 404 |
| 12 | 账号被删除后，已签发的会话仍然有效 | 删除管理员无法立即吊销其会话（最长 12 小时） | `adminAuth` 校验会话对应的账号仍存在；新增 `Store.DeleteUser` |
| 13 | 仪表盘「共 N 个密钥」读的是不存在的 `tasks.keys` | 卡片永远显示 0 | 改读 `tasks.api_keys` |
| 14 | dry-run 的实测结果被渲染成「结论：未通过」 | 只做了连通性检查却显示为失败，误导运维 | 前端按 `dry_run` 分支渲染为「仅连通性检查，未验证配额键」 |

> 第 11 项是本次验证中最严重的缺陷，也暴露了测试方法的漏洞：冒烟测试只断言了
> HTTP 状态码，而「HTML 外壳 + 200」完全满足该断言。修复后补充的测试会同时校验
> **响应体的内容和 `Content-Type`**，并断言缺失资源返回 404 而不是外壳。

另有 2 处测试自身的错误预期被修正（`Rotator` 两次用量语义、Windows 路径分隔符），
不是实现缺陷。

## 10. 已知限制

- **prompt 是否生效未证实**：上游前端在该通道不发送 `prompt`；网关会转发该字段，
  但上游是否使用无法确认。
- **`showcase` 通道不可用**：已被上游登录墙拦截（`401 login_required`），
  因此默认走 `plain`，且 `plain` 通道只输出 9:16 竖屏。
- **代理与伪造 XFF 互斥**：配置代理后不再伪造请求头，配额按代理出口 IP 计算。
  在 Docker Desktop for Windows/macOS 上，容器无法通过 `172.17.0.1` 访问宿主机
  上监听 `0.0.0.0` 的服务；需要代理时请使用 `host.docker.internal`。
- **竞态检测未在本机执行**：`-race` 需要 cgo，本机无 C 编译器。
- **额度取决于上游策略**：上游随时可能调整配额规则、增加校验或加登录墙。
  后台的实测页面可随时重新确认当前行为。
